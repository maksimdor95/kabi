# Модуль: dialogue_agent

## 1. Назначение
Ядро «менеджера»: ведёт онбординг и свободный диалог, извлекает структуру из речи
пользователя, обновляет профиль. Реализует **оркестрацию агентного цикла**
(orchestration в терминах агента).

## 2. Этап
M1 (онбординг + извлечение профиля), дозревает как советник на **M9**.

## 3. Публичный интерфейс
```python
async def handle_message(user_id: UUID, text: str) -> AgentReply: ...
async def run_onboarding_step(user_id: UUID, text: str | None) -> AgentReply: ...
```
`AgentReply` = сообщение пользователю + опциональные действия (обновить профиль, задать
следующий вопрос).

## Сценарий онбординга (решено)

Философия: менеджер сначала делает домашку (CV + публичные источники), потом задаёт
только то, что нельзя вывести. Для каждого поля профиля — одна из 4 стратегий:
**PARSE** (из CV) · **ENRICH** (из публичных источников пользователя, с согласия) ·
**INFER+CONFIRM** (вывести и подтвердить) · **ASK** (спросить напрямую).

Порядок шагов:

- **Шаг 0 — CV.** Пользователь присылает файл → `profile.parse_cv` → черновик профиля
  (в т.ч. `salary_expectation`, если указана в резюме).
- **Шаг 1 — Согласие + ссылки.** Просим ссылки на публичные источники
  (HH, LinkedIn, выступления, личный сайт). Разблокирует `enrichment`.
- **Шаг 2 — Приоритет:** работа / выступления / оба? (влияет на состав подборки)
- **Шаг 3 — Зарплата** (только если нет в CV): минимум для хард-фильтра вакансий.
- **Шаг 4 — Красные флаги:** куда НЕ предлагать (хард-фильтр по тексту вакансии).

**Не спрашиваем (не влияют на мэтчинг сейчас):**
- `job_search_status` — дефолт `passive`, в ранжировании не используется.
- `availability` (занятость / срок выхода) — в мэтчинге не используется.

**Дефолты (если пользователь пропустил):**
- Приоритет → **«оба, но вакансии первыми»**.
- Красные флаги → пусто (не фильтруем по анти-предпочтениям).
- Зарплата → **дефолта нет**; если нет в CV — вопрос обязателен.

**Критерий «онбординг завершён»:** заполнены обязательные поля профиля
(`ready_for_matching`, см. `profile.md`) + получено согласие на обогащение.

## 4. Входы / Выходы
- **Вход:** текст пользователя, текущее состояние онбординга/сессии.
- **Выход:** ответ пользователю; вызовы `profile` для обновления профиля.

## 5. Зависимости
- **Внутренние:** `app/llm` (модель + промпты), `app/services/profile`, память сессии (Redis).
- **Внешние:** —

## 6. Данные
Пишет через `profile` в `Profile`. Хранит краткосрочное состояние диалога в Redis.

## 7. Guardrails / ограничения
- Собирает данные только о самом пользователе.
- Не выдумывает факты о пользователе; при неуверенности — уточняет вопросом.
- Ограничение длины истории в контексте (windowed session history) ради OpEx.

## 8. Тесты / evals
- **Eval:** по реплике пользователя агент корректно извлекает поля профиля
  (навыки/локация/зарплата) — размеченный датасет примеров.
- **Eval:** траектория онбординга задаёт нужные вопросы и не зацикливается.

## 9. Открытые вопросы
- Насколько «проактивен» тон? Насколько часто агент сам инициирует диалог.
- Формулировки вопросов (тон «менеджера») — довести на этапе промптов.

## 10. Статус
M1: онбординг по шагам + свободный чат. Поведение:
- «начать заново» / первый CV на шаге 0 сбрасывает `source_links` и согласие
  (мягкий рестарт онбординга; CV-поля остаются). Полный wipe — команда `/delete`
  в боте (`profile.delete_account`), не здесь.
  (не тащим чужой LinkedIn с прошлого прогона).
- На шаге согласия новые ссылки **заменяют** старые; «Пропустить» очищает список.
- PDF с URL в подписи обрабатывается сразу (без повторного «пришли ссылки»).
- После CV не дублируем простыню про ссылки — один вопрос шага.
- Подтверждения CV/ссылок короткие («обновил из резюме» / «учёл ссылки в профиле»),
  детали — только в `/profile`; без повторного CTA на `/profile` в каждом пузыре.
- PDF mid-онбординга не зовёт `start_onboarding` и не переспрашивает текущий шаг.
- Вопрос про приоритет явно объясняет варианты Работа / Выступления / Оба
  и куда это попадает (`/today` / `/pitch` / `/talks`).
- Шаги `status` и `availability` убраны из онбординга (не участвуют в мэтчинге).
- Зарплата: PARSE из CV → шаг пропускается; иначе ASK (хард-фильтр вакансий).
- `hard_nos` — единственный оставшийся «мягкий» ASK, реально фильтрует подборку.

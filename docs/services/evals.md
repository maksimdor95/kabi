# Модуль: evals

## 1. Назначение

Контракт качества агента-менеджера: **что значит «подборка и объяснение
хорошие»**, как это измерять и когда релиз/регресс считается fail.

Модуль **не** ищет вакансии и **не** генерит продакшен-карточки. Он задаёт
методологию, датасеты и критерии. Код runner’а (`scripts/run_*_eval.py`) —
реализация этой спеки (отдельный PR после утверждения порогов).

Зачем: гипотеза MVP — «открыл подборку и сказал: это реально про меня»
(`SPEC.md` §9). Без evals нельзя отличить улучшение от поломки промпта,
фильтра или нового источника (M7).

## 2. Этап

**M8.** Зависит от стабильного `matching` + `explain` (M2–M4). Желательно
после первого среза M7 или параллельно с тонким эталоном на HH/SJ, с
переразметкой при смене пула источников.

## 3. Публичный интерфейс (контракт, не код)

Три поверхности:

| Поверхность | Вопрос | Метрика |
|-------------|--------|---------|
| **E1 Ranking** | В топе N — свои, не мусор? | precision@N, noise@N |
| **E2 Explain** | Reason фактологичен и полезен? | rubric score ≥ порога |
| **E3 Hard filters** | Очевидный брак отсечён? | recall отсечения на gold-negatives |

Unit-тесты (`tests/test_matching_filters.py`) покрывают детерминированные
фильтры — это **не** замена E1/E2. E3 дополняет их размеченным набором
«должна отвалиться» / «должна пройти фильтр, но может проиграть rank».

## 4. Входы / Выходы

- **Вход:** эталонный профиль (фикстура), пул `Opportunity` (фикстура или
  снимок БД), опционально сохранённые `reason` для offline-judge.
- **Выход:** отчёт eval-run (pass/fail по порогам) + артефакты для разбора
  (топ-N, scores, reasons, judge-комментарии).

Продакшен Telegram / scheduler **не** читает evals в runtime.

## 5. Зависимости

- **Внутренние:** `matching` (rank + explain), `profile` (фикстура профиля),
  опционально `digest` (если eval гоняет тот же limit/scope, что `/today`).
- **Внешние:** LLM для E2 (judge, tier cheap/primary — зафиксировать в run
  config); для E1 LLM не обязателен, если rank уже посчитан.

## 6. Данные

### 6.1. Каталог (предполагаемый layout после реализации)

```
evals/

  matching/
    profiles/
      marina_v1.json        # эталонный профиль (первый пользователь / anonymized)
    pools/
      jobs_hh_sj_v1.jsonl   # вакансии + лейблы
      pitch_v1.jsonl        # опционально, фаза 2
    gold/
      filter_negatives_v1.jsonl
    rubrics/
      explain_v1.md         # копируется/ссылается из §8.2 этой спеки
  reports/                  # gitignore: сырые прогоны
```

Opportunity в пуле — **снимки**, не live-API: стабильный регресс. Live-smoke
(«сегодняшний /today глазами человека») — отдельный ритуал, не CI-gate.

### 6.2. Схема профиля-фикстуры

Минимум полей, как у готового к мэтчингу профиля (`profile.md`):

```json
{
  "id": "marina_v1",
  "roles": ["Head of Product", "Product Lead", "CPO"],
  "location": "Москва",
  "work_mode": "hybrid",
  "skills": ["…"],
  "languages": ["…"],
  "speaking_topics": ["…"],
  "salary_expectation": {"min": 500000, "currency": "RUB"},
  "priorities": "both",
  "hard_nos": {"raw": "гемблинг, табак"},
  "goals": null,
  "notes": "Эталон под первого пользователя; не PII третьих лиц."
}
```

Эмбеддинг в фикстуре **не** коммитим (провайдер/модель могут смениться).
Runner считает embedding при прогоне или подтягивает из env-кэша.

### 6.3. Схема строки пула (JSONL)

Одна строка = одна возможность + разметка:

```json
{
  "id": "job_hh_123",
  "type": "job",
  "title": "…",
  "org": "…",
  "description": "…",
  "location": "Москва",
  "remote": true,
  "salary": {"min": 450000, "max": 700000, "currency": "RUB"},
  "url": "https://…",
  "source": "hh",
  "external_id": "…",
  "meta": {},
  "label": "relevant",
  "label_reason": "CPO/Head of Product, product platform, Москва/hybrid, вилка ок",
  "labeler": "human",
  "labeled_at": "2026-07-27",
  "scope": "jobs"
}
```

| Поле | Значения / правила |
|------|-------------------|
| `label` | `relevant` \| `borderline` \| `noise` |
| `label_reason` | 1 предложение: почему так (для обучения разметчиков и споров) |
| `scope` | `jobs` \| `pitch` \| `talks` — с каким `/`-потоком сравниваем |

**Семантика лейблов**

- **relevant** — «менеджер должен был принести»: роль/уровень/домен близки,
  вилка и формат не противоречат, нет hard-no. Человек сказал бы 👍 или save.
- **borderline** — спорно: соседний домен, ниже/выше уровнем, вилка на грани.
  В precision@N **не** считаем ни hit, ни noise (исключаем из знаменателя
  или отдельная метрика; см. §8.1).
- **noise** — не должен попасть в топ: другой трек (junior/sales), hard-no,
  офис при remote-only, зарплата явно ниже, «вакансия ради вакансии».

### 6.4. Размер и состав пула (фаза 1 — jobs)

| Класс | Целевой объём | Доля |
|-------|---------------|------|
| relevant | 15–25 | ~30–40% |
| borderline | 8–15 | ~15–25% |
| noise | 25–40 | ~40–50% |
| **Всего** | **50–80** | 100% |

Правила набора:

1. Брать из реальных прогонов `/today` и «почти попало / не попало», не
   выдумывать вакансии с нуля (иначе eval оптимизирует фантазию).
2. Явно покрыть failure modes: низкая ЗП, hard-no индустрия, office-only при
   remote, другой трек (backend-only), слишком junior, не тот город без remote.
3. Версионировать пул (`jobs_hh_sj_v1` → `v2` при M7). Старые отчёты
   ссылаются на id версии пула.

Фаза 2 (после стабилизации jobs): отдельный пул `pitch_v1` / `talks_v1` с
теми же лейблами; пороги могут отличаться (меньше relevant в природе CFP).

## 7. Guardrails / ограничения

- **Только данные пользователя-эталона** (или синтетика без PII третьих лиц).
  Чужие резюме в датасет не кладём.
- Eval **не** ходит в продакшен-БД на запись; read-only snapshot ок.
- LM-judge не является источником истины для `label` ранжирования — только
  для фактологичности reason. Лейблы relevant/noise — human (или human+review).
- Не оптимизировать промпт `explain` под конкретные фразы judge’а
  (adversarial overfitting). Rubric — про факты и полезность, не стиль.
- Пороги меняем только осознанно (запись в §9 / changelog спеки), не «подгоняем
  под зелёный CI» без изменения гипотезы.

## 8. Методология и пороги

### 8.1. E1 — качество подборки (ranking)

**Процедура**

1. Зафиксировать профиль `marina_v1` (или актуальный id).
2. Прогнать тот же пайплайн, что влияет на `/today`: hard filters → vector
   rank → top-N. **N = 7** (как `_DEFAULT_LIMIT` в matching), scope=`jobs`.
3. Сопоставить top-N с лейблами пула (по `id` / `source+external_id`).

**Метрики**

\[
\text{precision@N} = \frac{\#\{\text{relevant в top-N}\}}{\#\{\text{элементы top-N с лейблом relevant или noise}\}}
\]

Borderline в top-N **не входят** в числитель и знаменатель precision
(иначе споры съедают сигнал). Отдельно:

\[
\text{borderline@N} = \frac{\#\{\text{borderline в top-N}\}}{N}
\]

\[
\text{noise@N} = \frac{\#\{\text{noise в top-N}\}}{N}
\]

Опционально (если в пуле много relevant): recall@K среди всех relevant
(K=N или K=15) — «не потеряли ли очевидное».

**Пороги фазы 1 (gate M8)**

| Метрика | Pass | Fail / эскалация |
|---------|------|------------------|
| precision@7 | **≥ 0.57** (≥4 relevant из 7 «жёстких» слотов; на практике ≥4 relevant при ≥6 non-borderline) | < 0.50 |
| noise@7 | **≤ 2/7** (≈0.29) | ≥ 3/7 |
| borderline@7 | информативно; алерт если **≥ 5/7** (ранжир не различает) | — |
| recall@15 (relevant) | **≥ 0.60** | < 0.40 |

Интерпретация: менеджер может принести 1–2 спорных; **три и больше явного
мусора в семёрке** — доверие убито. Precision считаем по non-borderline, чтобы
не наказывать за честную серую зону.

**Регрессия:** относительно предыдущего зелёного прогона на **том же**
`pool_version` падение precision@7 > 0.15 или рост noise@7 на ≥2 карточки —
fail, даже если абсолютный порог ещё «зелёный».

### 8.2. E2 — качество объяснения («почему ты»)

**Что оцениваем:** текст `Match.reason` / `explain(profile, opp)` для
карточек из top-N (и отдельно для 5 фиксированных gold-пар
profile×opp с эталонными «хорошими» и «плохими» reason-образцами).

**Rubric (0–2 по каждому критерию; сумма 0–8)**

| ID | Критерий | 0 | 1 | 2 |
|----|----------|---|---|---|
| R1 | **Факты** | Есть выдумка / факт не из профиля и не из карточки | Мелкая натяжка | Только проверяемые факты |
| R2 | **Специфика** | Универсальная вода («отличная роль») | Общее, но с 1 якорем | ≥2 конкретных якоря (роль, навык, тема, формат, домен) |
| R3 | **Честность fit** | Игнорирует явный мисфит | Частично | Если fit слабый — не приукрашивает (или карточка relevant и reason это отражает) |
| R4 | **Полезность** | Не помогает решить 👍/👎 | Слабо помогает | Понятно «зачем мне это открывать» |

**Запрещено в reason (авто-fail R1=0):** зарплата/компания/навык, которых нет в
входах; «ты работал в X», если X нет в experience профиля; выдуманный дедлайн.

**Как судить**

1. **Human** (фаза старта): 2 прохода по одним и тем же 7+5 reasons, сверка
   расхождений.
2. **LM-judge** (автоматизация): тот же rubric в system-prompt; на вход —
   профиль (сжатый), карточка, reason; на выход — JSON `{scores, brief}`.
   Калибровка: agreement с human ≥ 0.7 по R1 (факты) на 20 примерах до
   включения в CI-gate.

**Пороги фазы 1**

| Метрика | Pass |
|---------|------|
| Доля reason с суммой rubric ≥ 6 | **≥ 80%** на top-7 |
| Доля с R1 = 2 (чистые факты) | **≥ 90%** |
| Доля с R1 = 0 (выдумка) | **= 0%** (жёсткий gate) |

Fallback-строки matching («Совпадение по роли…») при ошибке LLM: для eval
считать **fail по R2** (не специфично), не по R1 — чтобы не маскировать
деградацию explain.

### 8.3. E3 — хард-фильтры на gold-negatives

Отдельный маленький набор (15–30 шт.), где ожидается `passes_hard_filters ==
False` (низкая ЗП, hard-no, closed CFP, office при remote-only, …).

| Метрика | Pass |
|---------|------|
| Доля корректно отсечённых | **≥ 95%** |

Это почти unit, но на реалистичных текстах вакансий (org/description), не
только на синтетических SimpleNamespace. Unit-тесты остаются; E3 ловит
регрессии парсинга salary/meta.

### 8.4. Что сознательно не измеряем в M8

- Красота формулировок / тон «менеджера» (это M9).
- Online CTR / 👍 rate в проде — **северная звезда**, но шумная и медленная;
  evals — ведущий индикатор, прод-фидбек — подтверждающий.
- Полнота рынка («нашли все вакансии мира») — зона ingestion/M7.
- Latency `/today` — observability, не quality-eval.

### 8.5. Ритуал прогона (когда runner появится)

| Триггер | Что гоняем | Gate |
|---------|------------|------|
| PR, меняющий `matching` / `explain` / фильтры | E1 (без LLM если scores из кэша) + E3 | да |
| PR, меняющий промпт explain | E2 (LLM) | да |
| Новый источник M7 | новый pool_version + переразметка ≥20 items | да перед merge источника в default digest |
| Weekly | полный E1+E2+E3 на актуальном эталоне | алерт в лог, не блок merge |

## 9. Открытые вопросы

1. **Эталон один или несколько профилей?** Сейчас single-user → один
   `marina_v1`. При втором пользователе — второй профиль + те же пулы с
   лейблами *относительно* профиля (лейблы не абсолютны).
2. **Borderline в precision:** исключаем (как выше) vs считаем half-credit.
   Стартуем с exclude; пересмотрим после 2–3 прогонов.
3. **Эмбеддинги в CI:** мок vs реальный Yandex. Реальный — ближе к правде,
   дороже и флакучее. Компромисс: кэш embedding векторов в
   `evals/matching/cache/` (не секреты) + пересчёт по флагу.
4. **Порядок vs M7:** ~~тонкий pool v1~~ → **`jobs_m7_v2`** после M7 (методология
   та же; v1 остаётся для регрессии HH-only).
5. Нужен ли отдельный eval черновиков (`drafts`) в M8? Нет — оставить в
   `drafts.md`; M8 = подборка + why-you.

# ADR 0001 — Модульный монолит вместо микросервисов

- **Статус:** принято
- **Дата:** 2026-07
- **Контекст-источник:** *The New SDLC With Vibe Coding* (factory model, «structure scales»)

## Контекст

Kabi на старте — single-user MVP (один пользователь). Нужно быстро проверить
продуктовую гипотезу, но не создать себе «спагетти», которое дорого поддерживать.
Стоял выбор: микросервисы vs монолит.

## Решение

Строим **модульный монолит**: один разворачиваемый процесс, жёсткие внутренние
границы модулей, зависимости направлены к домену.

- `bot/` — тонкий интерфейс, без бизнес-логики.
- `app/` — ядро (домен + приложение + инфраструктура).
- Общение между модулями — через явные интерфейсы сервисов, не через сеть.

## Обоснование (по статье)

1. **CapEx туда, где важно.** Статья: инвестируй в спеки, контекст, тесты/evals,
   guardrails — а не в distributed-инфраструктуру. Микросервисы = высокий OpEx
   (сеть, разворачивание, наблюдаемость N сервисов) без ценности для одного юзера.
2. **Архитектура — человеческая фаза trade-offs.** Мы осознанно выбираем простоту.
3. **Агентная природа.** Агенту удобнее общий session state и синхронные вызовы
   инструментов внутри процесса, чем сетевые хопы между сервисами.

## Последствия

- (+) Быстрая разработка, простой локальный запуск, дешёвый рефакторинг.
- (+) Границы модулей проведены → вынос в сервис позже дёшев.
- (−) Один процесс масштабируется вертикально; при росте нагрузки на `ingestion`/
  `matching` их выносим отдельно (см. overview → «границы для выноса»).

## Когда пересмотреть

- Появляется multi-user с заметной нагрузкой.
- `ingestion` требует независимого масштабирования/расписаний под многие источники.
- Нужен отдельный язык/рантайм под какой-то модуль.

# ADR 0002 — Kabi как агент + харнесс, а не «просто бот»

- **Статус:** принято
- **Дата:** 2026-07
- **Контекст-источник:** *The New SDLC With Vibe Coding* (Agent = Model + Harness)

## Контекст

Продукт легко было бы свести к «телеграм-бот, который дёргает job-API». Но ценность
(«менеджер знает тебя и приносит только твоё») требует агентного поведения:
рассуждение, использование инструментов, память, самокоррекция на фидбеке.

## Решение

Проектируем Kabi как **AI-агент** с явным разделением **модель vs харнесс**.

- **Модель** — только движок рассуждения (`app/llm`), заменяемый.
- **Харнесс** (наш код и его ценность):
  - **Instructions / rule files:** `AGENTS.md`, промпты (`app/llm/prompts`).
  - **Tools:** сервисы и коннекторы (`app/services/*`, `app/ingestion`) как инструменты.
  - **Memory:** `app/db` (профиль, матчи, фидбек) + Redis (сессии).
  - **Orchestration:** `dialogue_agent` + `scheduler` (агентный цикл).
  - **Guardrails:** hard rules из `AGENTS.md`, валидации, лимиты.
  - **Observability:** `app/observability` — логи, трейсы, учёт токенов/стоимости.

## Обоснование

- «Большинство сбоев агента — это сбои конфигурации харнесса, а не модели.» Значит,
  ценность и надёжность мы строим в харнессе, а модель держим заменяемой.
- **Роутинг моделей:** мощная модель для сложного (диалог, мэтчинг-объяснения),
  дешёвая — для рутины (нормализация, классификация). Снижает OpEx токенов.

## Последствия

- (+) Модель можно менять/удешевлять без переписывания продукта.
- (+) Явные guardrails и observability с самого начала → меньше «скрытого долга».
- (−) Больше upfront-структуры (CapEx), чем у «голого» бота. Это осознанно.

# AGENTS.md — Harness / правила проекта Kabi

> Этот файл — часть «харнесса» (по терминологии *The New SDLC With Vibe Coding*).
> Он загружается агентом всегда и определяет, кто он, как себя ведёт и что ему запрещено.
> Правила добавляются по мере того, как агент делает что-то, чего делать не должен.

## Что это за проект

**Kabi** — персональный AI-менеджер карьеры в Telegram. Он знает о пользователе всё
релевантное для карьеры и **проактивно** приносит подходящие вакансии и приглашения
на выступления/конференции. Метафора: «персональный менеджер, как у звезды».

Первый пользователь — один человек (single-user MVP). Мультиарендность откладываем.

## Природа системы

Kabi — это **AI-агент-продукт**, а не просто бот. Он реализует агентный цикл:
`perceive → plan → act (tools) → observe → iterate`. Проектируем через пять частей агента:
**model, tools, memory, orchestration, deployment**.

## Стек

- Python 3.12
- Telegram: `aiogram` (интерфейс — тонкий слой)
- Backend: `FastAPI` (health + позже API для Mini App)
- БД: PostgreSQL + `pgvector` (эмбеддинги)
- Кэш/очереди: Redis
- Планировщик: APScheduler
- LLM: провайдер-агностично через `app/llm` (роутинг моделей)
- Инфра: Docker Compose

## Архитектура (кратко)

Модульный монолит. Границы модулей — жёсткие. См. `docs/architecture/overview.md`
и ADR `docs/architecture/decisions/`.

- `bot/` — только интерфейс Telegram (хендлеры, клавиатуры). Без бизнес-логики.
- `app/` — ядро: агент, домен, инфраструктура.
- `docs/` — спека на архитектуру и по MD на каждый модуль.

## Hard rules (нельзя нарушать)

1. **Никакой бизнес-логики в `bot/`.** Бот только принимает ввод и рендерит вывод,
   вызывая сервисы из `app/`.
2. **Секреты только через переменные окружения** (`.env`, не коммитить). Никаких
   хардкод-токенов/паролей в коде.
3. **Домен не зависит от инфраструктуры.** `app/domain` не импортирует БД, сеть, LLM.
   Зависимости направлены внутрь (к домену).
4. **Каждый модуль имеет спеку** в `docs/services/<module>.md`. Меняешь поведение —
   обновляешь спеку в том же PR.
5. **Сбор данных о третьих лицах — под запретом.** Собираем данные только о самом
   пользователе и с его согласия. Источники возможностей — публичные/официальные.
6. **Тесты и evals — это контракт с агентом.** Для нетривиальной логики сначала
   договариваемся о критериях (что значит «правильно»), потом реализация.
7. **Стенд только из Git.** Сначала commit + push в `maksimdor95/kabi`, потом
   `git pull` на ВМ. Не катить незапушенное через rsync. См. `.cursor/rules/deploy-via-git.mdc`.

## Workflow

1. Спека модуля (`docs/services/*.md`) → 2. Тесты/evals-критерии → 3. Реализация →
4. Проверка (ревью каждой строки, что идёт в прод) → 5. Обновление спеки/статуса →
6. Push в Git → 7. Pull/restart на стенде.

## Контекст: статический vs динамический

- **Статический** (всегда в контексте): этот `AGENTS.md`, `docs/architecture/overview.md`.
- **Динамический** (по требованию): конкретная `docs/services/<module>.md`, релевантный код.

Держим статический контекст плотным и коротким. Детали — в спеках модулей.
